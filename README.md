# 霜ばしら 予約販売開始・再入荷 監視ボット v2（GitHub Actions + Discord）

九重本舗玉澤の「霜ばしら」（`https://tamazawa.thebase.in/items/33921076`）を対象に、

1. **商品ページの在庫ステータス**を監視し、買えるようになった瞬間を検知
2. **受付開始の告知**（商品説明文・公式サイトのお知らせ・X の新着）を検知
3. 告知文から**開始日時を自動で読み取り、自動でアーミング**（開始前に高速監視へ切り替え）
4. すべて **Discord に通知**（購入ページをワンタップで開けるリンク付き）

を行うボットです。GitHub Actions 上で動くので PC を起動しておく必要はありません。

---

## ⚠️ 最初に読んでください

### 1. これは「自動購入ボット」ではありません

BASE の利用規約 **第18条 禁止行為 第33号** には

> クローリング（クローラ、ロボット又はスパイダー等のプログラム）、スクレイピング及びその他の類似の手段によって本サービスにアクセスし、又は本サービスに関する情報を取得する行為

と明記されています。機械的な自動アクセス全般が禁止されており、**このボットも厳密にはグレー**です。自動での「カート投入→決済確定」まで行う完全自動購入はリスクが大きく（アカウント停止・注文キャンセル）、BASE の決済は 3D セキュアが入るため技術的にも安定しません。

そこで本ボットは **「検知して人間に知らせる」まで** にとどめ、購入操作は自分で行う設計にしています。

### 2. 「ランダムな開始時刻」にどう対応するか

公式 X で「次回予約受付は ○日 19:00 頃より」と告知されるタイプなので、**告知をいかに早く掴むか**が鍵になります。本ボットは 3 系統で監視します。

| 情報源 | 何を検知 | 速さ | 信頼度 |
|---|---|---|---|
| **A. 商品ページ** | 在庫ステータス（購入可否）＋**商品説明文の書き換え**＋販売期間の設定 | 最速（秒単位） | ◎ 公式そのもの |
| **B. 公式サイト お知らせ** `tamazawa.jp/news/` | 新着記事（霜ばしら・予約・受付 のワード） | 分単位 | ○ 公式 |
| **C. 公式 X** | **投稿数が増えたこと**の検知 | 15 分間隔 | △ 本文は取れない |

**A が本命です。** 理由は、この店はこれまでも**商品説明文を告知文に書き換えてきた**からです（現在の説明文にも「9月23日（水）19時に受付を開始致しました」と明記されています）。説明文が書き換われば本ボットがそれを検知し、**本文から開始日時を推定して自動でアーミング**します。

> **X の注意点（正直な話）**: X のタイムライン本文は公式 API なしでは安定して取得できません。以前使えた `syndication.twitter.com` のエンドポイントは**古いキャッシュしか返さず、レート制限（HTTP 429）もありました**。そこで C は「投稿数が増えた＝何か投稿された」ことだけを検知して「X を確認してください」と知らせる方式にしています。日時が欲しいときは X を見て `START_AT` に手入力するのが確実です。

### 3. 隙間なく監視する仕組み

GitHub の `schedule`（cron）は最短 5 分間隔で、**数分〜十数分の遅延が普通にあります**。そこで本ボットは

- **1 回の実行で 420 秒（7 分）監視する**
- cron は 5 分ごとに起動する
- `concurrency` で直列化しているので、前の実行が終わり次第すぐ次が始まる

という構成にしています。**実行時間（420 秒）> cron 間隔（300 秒）** なので、cron が数分遅れても監視に隙間ができません。これが v1（290 秒 < 300 秒で隙間があった）からの最大の改善点です。

### 4. GitHub Actions の利用枠に注意

- **プライベートリポジトリ**では実行時間が無料枠（2,000 分/月）を食います。上記構成は 1 日で約 2,000 分消費するので、**1 日で枠が尽きます**。
- **パブリックリポジトリなら GitHub Actions は無料・無制限**です。Webhook URL は Secrets に入るので公開しても漏れません。**パブリックリポジトリを強く推奨します。**
- とにかく節約したい場合は `mode=window` で実行してください。開始ウィンドウの外では「1 周確認して即終了」になるため、**待機中の消費をほぼゼロ**にできます。
- GitHub は一定期間リポジトリに動きがないと `schedule` を無効化します。状態が変化したときだけ `state.json` が自動コミットされるので、活動ログも兼ねます。

## セットアップ

### 手順 1: リポジトリを作る

GitHub で **Public** リポジトリを新規作成し、この `tamazawa-watch` フォルダの中身を丸ごと push してください。

```
tamazawa-watch/
├── .github/workflows/watch.yml   # GitHub Actions の定義
├── monitor.py                    # 監視スクリプト本体（標準ライブラリのみ）
├── state.json                    # 監視状態（Actions が自動更新・コミット）
├── .gitignore
└── README.md
```

### 手順 2: Discord Webhook を取得

1. 通知したい Discord サーバー → チャンネルの ⚙️「チャンネルの編集」
2. 「連携サービス」→「ウェブフック」→「新しいウェブフック」
3. **ウェブフック URL をコピー**（`https://discord.com/api/webhooks/xxxx/yyyy`）

> スマホに確実にプッシュ通知を届けるには、Discord モバイルアプリを入れ、そのサーバーの通知を「すべてのメッセージ」に設定してください。

### 手順 3: GitHub に設定を登録

- **Settings → Secrets and variables → Actions → Secrets**
  - `DISCORD_WEBHOOK_URL` = 手順 2 の URL
- **同 → Variables**（任意）
  - `DISCORD_MENTION` = 例 `<@あなたのユーザーID>` / `@here`
- **Settings → Actions → General → Workflow permissions** を **「Read and write permissions」** に変更
  （`state.json` を自動コミットするため。忘れるとコミット手順だけ失敗します）

### 手順 4: 動作確認

**Actions → 霜ばしら 監視 → Run workflow** を実行します。初回は「基準の記録」だけを行い、検知通知はしません。ただし**手動実行のときは起動通知（🚀）が Discord に届きます**ので、Webhook の疎通確認にも使えます（起動通知が不要な場合は `NOTIFY_START=0`）。

```
[2026-10-16 19:22:06 JST] 開始予定の告知はまだ検出していません。通常間隔で監視します。
[2026-10-16 19:22:06 JST] 前回の状態: status=unpurchasable
[2026-10-16 19:22:07 JST] [商品] status=unpurchasable
[2026-10-16 19:22:07 JST] お知らせ最新: [2026-09-12] 冬季限定商品「霜ばしら」 本店での店頭販売開始日のご案内 （変化なし）
[2026-10-16 19:22:07 JST] X 投稿数: 222 （基準として記録）
```

Discord 通知の見た目をローカルで確認したい場合（送信はされません）:

```powershell
cd tamazawa-watch
$env:DRY_RUN = "1"
python -c "import monitor as m; m.notify_purchasable({'price': 4860})"
python -c "import monitor as m; from datetime import datetime,timedelta; m.notify_announcement('テスト', '11月20日（金）19時より受付開始します', datetime.now(m.JST)+timedelta(days=5))"
python -c "import monitor as m; m.notify_start({'status': 'unpurchasable'}, None, '')"
```

## 使い方

### ふつうは何もしなくてよい（自動アーミング）

cron が 5 分ごとに動き続けます。告知（説明文の書き換え / お知らせ / X の新着）を検知すると、

- 「📢 受付開始の告知を検出しました」を Discord に通知
- 本文から開始日時を読み取り、`state.json` の `announced_start_at` に記録
- 以降はその時刻の **10 分前から自動で 2 秒間隔**に切り替え
- 購入可能になった瞬間に「🎉 販売開始 / 再入荷を検知しました」を 3 回通知

という流れになります。**人手の操作は不要**です。

### 自分で開始時刻を指定したい場合

X を見て日時が分かったら、**Run workflow** で `start_at` に直接入力するのが最も確実です。

| 入力 | 例 | 意味 |
|---|---|---|
| `start_at` | `2026-11-20T19:00:00` | 受付開始予定時刻（**JST**、秒は省略可） |
| `lead_minutes` | `10` | 開始 10 分前から高速監視に入る |
| `fast_interval_seconds` | `2` | 高速監視中の間隔 |
| `max_seconds` | `19800` | 監視し続ける秒数（19800 秒 = 5.5 時間） |
| `timeout_minutes` | `350` | ジョブのタイムアウト（`max_seconds` より大きく。**最大 360**） |

> 手動実行はキュー待ちになることがあります。**開始の 1〜2 時間前に起動**しておくと安心です。
> ジョブの上限は 6 時間です。それ以上先なら cron に任せるか、時間をおいて実行し直してください。

### 省エネで運用したい場合

`mode=window` にして実行すると、開始ウィンドウの外では 1 周確認して即終了するため、待機中の Actions 消費をほぼゼロにできます。**自動アーミングと組み合わせると、告知検知 → 自動でアーミング → 開始前になったら cron 実行が自然に高速監視へ、という流れになります。**

## 検知できること / 通知の種類

| 通知 | 条件 |
|---|---|
| 🚀 ボットを起動しました | 手動実行（Run workflow）で起動したとき |
| 🎉 販売開始 / 再入荷を検知 | 商品ページが `purchasable` になった（最重要・3 回再送） |
| 📢 受付開始の告知を検出 | 商品説明文 / お知らせ / から告知文と日時を検出 |
| 🐦 公式Xに新しい投稿 | X の投稿数が増えた（本文は取れないので確認を促す） |
| 📝 商品説明文が更新 | 説明文のハッシュ変化（`NOTIFY_TEXT_CHANGE=1` で有効） |
| 😢 売り切れに戻りました | `purchasable` → `unpurchasable`（`NOTIFY_SOLD_OUT=1` で有効） |

### 開始日時の読み取りについて

`10/24（月）19:00頃より`、`11月20日（金）19時より`、`11/3（火）10時` のような表記に対応しています。誤検知を避けるため、次の場合は**日時を採用しません**。

- 時刻が書かれていない（例:「11月20日より受付開始」）→ 日時は推定せず通知のみ
- すでに過去の日時（例: 終了済みの前回告知「9月23日19時」）
- 45 日より先の日時（誤読とみなす）

推定に失敗しても通知は届くので、その場合は X などで確認して `START_AT` に設定してください。

## state.json について

二重通知を防ぎ、自動アーミングの情報を次回実行へ引き継ぐためのファイルです。**内容が変化したときだけ** Actions がコミットします。

```json
{
  "status": "unpurchasable",
  "reason": "out_of_stock",
  "price": 4860,
  "changed_at": null,
  "item_description_hash": "355b9dfa8ab00d96",
  "item_description_excerpt": "ご好評につき、9月23日（水）19時に受付を開始致しました…",
  "news_latest_id": "detail.php?CN=434152",
  "news_latest_title": "冬季限定商品「霜ばしら」 本店での店頭販売開始日のご案内",
  "news_latest_date": "2026-09-12",
  "x_tweet_count": 222,
  "announced_start_at": "2026-11-20T19:00:00+09:00",
  "announced_source": "商品説明文",
  "announced_at": "2026-10-16 19:22:15 JST"
}
```

**リセットしたい場合**は `"status"` を `"unknown"` に、`"announced_start_at"` を削除して push してください。

## 監視の仕組み（何を見ているか）

BASE の商品ページ HTML には、テーマが埋め込む Google Tag Manager 用の `dataLayer` があり、そこに購入可否が入っています。

```js
window.dataLayer.push({
  'item_purchasability': "unpurchasable",
  'item_unpurchasable_reason': "out_of_stock",
  'itemPrice': 4860,
});
```

本スクリプトはこの `item_purchasability` を正規表現で抽出して判定します。併せて `SOLD OUT` 要素・メンテナンス文言・`salesPeriod--*`（販売期間）も見て、誤検知を防いでいます。キャッシュを掴まないよう `Cache-Control: no-cache` とキャッシュバスターを付けています。

公式サイトのお知らせは `<th scope="row">日付</th><td><a href="detail.php?CN=...">タイトル</a>` という素直な表なので、最新記事の ID 変化で新着を検知し、本文から日時を拾います。

## さらに確実にしたい場合

1. **公式の「再入荷メール通知」も併用する** — 商品ページの SOLD OUT 付近の「再入荷通知」からメール登録できます（BASE 純正）。通知経路が二重になります。
2. **BASE アカウントと住所・カードを登録しておく** — ログイン済みなら入力の手間が減り、決済が速くなります。
3. **開始直前は商品ページを開いたまま待機する** — 通知が来たらワンタップで購入へ。**カート投入ではなく「決済完了」が購入確定**です（店側の説明より）。
4. **スマホと PC の両方で Discord を見る** — Discord のモバイルアプリならプッシュ通知が即届きます。

## トラブルシューティング

| 症状 | 対処 |
|---|---|
| Discord に通知が来ない | `DISCORD_WEBHOOK_URL` を確認。ローカルで `DRY_RUN=1` を付けて送信内容を確認 |
| `state.json` のコミット手順で失敗する | Settings → Actions → General → Workflow permissions を「Read and write permissions」に |
| X の取得で 429 / 失敗ログが出る | 仕様です（外部サービス依存）。`X_INTERVAL_SECONDS` を延ばすか `ENABLE_X=0` |
| 開始日時が推定されない | 本文に時刻が無い可能性。X を確認して `START_AT` に手入力 |
| ステータスが `unknown` のまま | 商品ページの構造変更の可能性。`monitor.py` の正規表現を実ページに合わせる |
| Actions が動かなくなった | 60 日間動かないと `schedule` が無効化される。Actions タブで再度 Enable |
| 誤検知で通知が飛んだ | `state.json` の `announced_start_at` を削除、`status` を `unknown` に戻す |
